## v0.23.1 — PostgreSQL connection pool fixes

Addresses connection exhaustion seen in cluster-mode deployments where each
worker was opening an unbounded pool of connections, quickly exceeding Postgres's
`max_connections` limit and causing `"too many clients already"` errors.

### Fixes

- **Postgres: cap connections per worker pool.** `PostgresAdapter` now accepts
  `PG_POOL_MAX` (default `2`) and `PG_CONNECT_TIMEOUT_MS` (default `5000 ms`)
  from config. Previously the `pg.Pool` ran with its library default of `max: 10`
  per process — with `CLUSTER_ENABLED` forking `N` workers, the total connection
  count was `N × 10`, easily blowing past typical hosted Postgres limits (25–100).
  Now the pool is bounded by `PG_POOL_MAX` per worker. Tune via env:
  `PG_POOL_MAX = floor(pg_max_connections / num_workers) - headroom`.

- **Postgres: fail fast on pool exhaustion.** With `PG_CONNECT_TIMEOUT_MS=5000`,
  requests that cannot acquire a pool slot within 5 s get an immediate error
  rather than queuing silently and piling up. Set to `0` to restore the previous
  unlimited-wait behaviour.

- **Postgres: drain pool on shutdown.** Workers now register `SIGTERM`/`SIGINT`
  handlers that call `db.close()` (`pool.end()`) before exiting. Previously,
  connections were abandoned on process exit — Postgres saw abrupt TCP resets
  and the slots weren't released until its own TCP timeout. Clean drain means
  restarted workers start fresh without fighting over inherited connection slots.
