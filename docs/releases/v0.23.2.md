# a-workbench v0.23.2

_2026-08-14_

Headline: **API key verification is now O(1) — indexed SHA-256 lookup replaces a full-table bcrypt scan.**

## Performance

- **`verifyApiKey` — indexed lookup via `api_key_sha`.** Every `/mcp` request previously scanned every row in `users` and ran `bcrypt.compareSync` against each hash in turn. This was O(n·bcrypt_cost) event-loop-blocking work: about 2.8s at 100 users, and the MCP handshake is two requests so a cold connect paid it twice (~9.2s on staging). The new `api_key_sha` column stores a SHA-256 of each key; a partial index on that column makes lookup a single `SELECT WHERE api_key_sha = ?`.

  Migration is fully automatic and zero-downtime:
  - Schema: `ALTER TABLE users ADD COLUMN api_key_sha TEXT` + `CREATE INDEX … WHERE api_key_sha IS NOT NULL` runs at startup (both SQLite and Postgres paths). No manual step needed.
  - Data: legacy rows (without `api_key_sha`) fall back to the bcrypt scan on first verify, then get the sha written immediately so subsequent calls take the fast path. New keys (created or rotated after this version) always use the fast path.

  SHA-256 with no work factor is correct here because keys are `crypto.randomBytes(32)` minted server-side — never user-chosen. 256 bits of entropy makes a preimage attack on the stored digest infeasible. OAuth Bearer and session JWT callers were never affected (signature-only verify, no DB scan).

- **`bcrypt.compareSync` → `bcrypt.compare` in the legacy fallback.** The synchronous variant blocked the event loop for the full bcrypt cost factor. Async compare is now used so the loop stays free during the fallback path.

## Fixes

- **`resolve.ts`: missing `await` on `verifyApiKey`.** The function is async; the caller was not awaiting it. It received a Promise object, which is always truthy, so `if (u) return u` always passed — returning a Promise instead of a user ID. Any API key header may have been silently accepted before this fix. The `await` is now present and auth is correctly enforced on the API key path.

## Tests

- New test: `verifies a legacy bcrypt-only key and backfills its sha` — creates a user, NULLs `api_key_sha` to simulate a pre-migration row, verifies it still works via the bcrypt fallback, confirms the sha is written, then verifies again to confirm the fast path is taken on the second call.
