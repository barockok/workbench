# a-workbench v0.24.0

_2026-08-26_

Headline: **Curl proxy — transparent API access via short-lived session tokens.**

## Features

- **`curl_session` meta-tool + `/c/<integration>/<path>` transparent proxy** (`packages/server/src/mcp/meta-tools.ts`, `packages/server/src/auth/curl-session.ts`, `packages/server/src/api/curl-proxy.ts`). An agent calls `curl_session({integrations: [...]})` and gets back a 15-minute signed JWT (`jose`, HS256). Any request to `/c/<integration>/<path>` carrying that token as a Bearer header is forwarded to the integration's real API — all HTTP methods (GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS) — with the user's real credential (OAuth2 bearer, API key, or cookie) injected server-side and hop-by-hop headers stripped/rewritten. This gives agents raw REST access to an integration beyond whatever purpose-built tools already exist for it, at the cost of no per-path or per-method restriction: a token scoped to `github` can call anything under GitHub's API the connected credential can reach.
- **Per-integration opt-in.** A new `proxy` field on the integration manifest gates which integrations accept `curl_session` tokens at all. Enabled this release on asana, atlassian-bitbucket, atlassian-confluence, atlassian-jira, github, gitlab, google-calendar/docs/drive/gemini/gmail/sheets/slides, newrelic, and slack.
- **Dynamic base-URL resolution** (`packages/server/src/api/curl-proxy.ts`). Integrations whose API host isn't a fixed string resolve it per-connection: jira/confluence read `instanceUrl` from the stored connection config, gitlab supports self-hosted instances the same way, and newrelic switches between US and EU GraphQL endpoints based on the connection's `region`.
- **High-risk guardrail on the tool description.** `curl_session`'s description now opens with an explicit HIGH RISK flag, names the concrete risk (arbitrary methods including destructive writes, real credential injected), and instructs the calling agent to state which integration(s) and what action it intends before minting, and to wait for explicit user approval rather than minting speculatively. This is a prompt-level instruction the calling agent is expected to follow — there is no server-side approval gate or read/write scoping in the JWT itself. A coarse (approve every mint) or fine-grained (read-only-by-default token, separate approval to escalate) code-level gate remains a follow-up if a hard block is wanted instead.
